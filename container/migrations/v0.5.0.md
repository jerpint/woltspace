# v0.5.0 — the colony leaves the container

**Required?** No. Everything works without it. This consolidates two directory names the
platform now reads from both places, so the lodge stops carrying the older one forever.

**Coming from:** any 0.4.x lodge.

## What changed

"Projects" are "apps". New apps are created under `wolts/apps/`, the routes are `/apps/…`,
and the app skills answer to the new name. Apps still sitting in `wolts/projects/` are
discovered and served exactly as before — the rename is backwards compatible, which is why
this document is optional.

The manifest schema (`woltspace.json`) did not change. Nothing inside an app moves.

## Steps

1. **Confirm what you have.** List the wolts directory. If there is no `projects/`, you are
   already done — say so and stop.
2. **Move `projects/` to `apps/`.** If only `projects/` exists, it is a rename. If both
   exist, the contents merge into `apps/` and `projects/` stays behind as a backup for the
   human to remove when they are ready.
3. **Drop the stale running-state directory.** `.space/projects/` holds only live state and
   is recreated as `.space/apps/` on the next start. It is safe to delete; it is not safe
   to guess about, so say what you are deleting first.
4. **Rename the field in session records.** Session JSON files that carry a `project` key
   get an `app` key with the same value. Untouched files stay untouched.

A script beside this document does all four and is safe to run twice:

```bash
bash <install_root>/container/migrations/v0.5.0.sh <wolts directory>
```

Show the human what it does before you run it. It takes the wolts directory as an argument
rather than reading it from the environment, so pass the one `woltspace paths` reports.

## After

Nothing to restart — the platform already reads both names, so the move changes only where
new apps land. Tell the human if a `projects/` backup was left behind.
