# Migrating to 0.6.0: the Mill

**For:** every lodge coming from 0.5.x. **Required:** yes, for anyone who reaches apps through a tunnel, and for a lodge in a container (Docker or the desktop app) that has apps. Otherwise there's little to do.

**Why:** apps used to be reachable on the lodge's own origin, where their script could call the lodge's API as the owner. In 0.6 each app has an origin of its own, served by the Mill. See `docs/mill.md`.

## What changed

- **Wolt sites don't change:** they stay at `/wolt/<wolt>/site/` on the lodge, with the nav shell and live reload, locally and through the tunnel. Giving sites an origin of their own is a later change.
- **Apps:**
  - Apps live at `http://<app>.localhost:7777/`, unchanged.
  - Through the tunnel, they're at `https://<app>.<your domain>/`, unchanged.
  - Both go through the Mill now.
  - `/app/<app>/` redirects there. Static apps (no `start`) are served by the Mill, without their dotfiles.
- **Sharing is explicit, and goes through the Mill:** `woltspace app share <app>` shares one app with anyone who has the link, through the lodge and the Mill (see `docs/mill.md`). `"public"` in an app's manifest no longer shares it, and `WOLTSPACE_SHARING_ENABLED` is gone. The old per-app quick tunnels, which reached an app's port directly, are retired. At first boot, the lodge stops the quick tunnels an older lodge started, but only a process whose command is still that app's quick tunnel. It clears a record only once the tunnel has stopped, and leaves that app untouched until then. `woltspace doctor` fails while one is still running.
- **Through the tunnel, the lodge checks Cloudflare Access itself:** an app is opened only for a valid Access token for the apps' Access application, and only for the owner's email. That needs `ways_in.cloudflare` settings (below). Without them, apps through the tunnel answer `403`.
- **App names:** an app named `site-…` is no longer served, locally or through the tunnel, because the name is reserved for wolt sites. Rename it (`woltspace doctor` names it).
- **Sparks and tool pages** (`/history/…`, `/tools/…`) run in an opaque sandbox on the lodge's origin.

## Steps

1. **Links:** site links don't change. Links to an app's old `/app/<app>/` address keep working through a redirect; new ones use `http://<app>.localhost:7777/`.

**If someone gave the owner a connection code** (it starts `woltspace-cloudflare-1.`): skip steps 2 and 3 and follow `connect.md` in the Cloudflare skill. It runs `woltspace connect cloudflare`, which saves the same settings and brings the tunnel up, and it needs nothing on Cloudflare from the owner.

**If the lodge runs in a container** (Docker or the desktop app) and has apps: with lodge auth off, an app is the owner's only for a browser on the same machine that connects straight to the lodge, and through Docker's port forwarding it never is, so every app answers `403`. Turn lodge auth on: set `WOLTSPACE_LODGE_AUTH=1` in the lodge's `.env`, restart the lodge, then run `woltspace pair` and open the link it prints (see `docs/lodge-auth.md`). `woltspace doctor` warns (`container-apps`) until it's on.

2. **Only the owner can do this, on Cloudflare:** apps need an Access application covering `*.<your domain>`. If you followed `docs/wildcard-subdomain-setup.md` or the cloudflare skill, you already have one (`woltspace-apps`): reuse it. One application can also cover the lodge; a second one for the lodge is optional, and lets the two have different policies. If you have one, add its AUD as `"lodge_aud"` next to `apps_aud` below, or your login won't open the lodge. You need the AUD tag of the one covering `*.<your domain>`: Zero Trust → Access → Applications → the application → Overview → "Application Audience (AUD) Tag" (or `result.aud` from the API). An app with an Access application of its own has a different AUD and answers `403` through the tunnel: remove that application, so the wildcard one covers the app.
3. **Only the owner can do this, in `woltspace.json`:**
   ```json
   "ways_in": {
     "cloudflare": {
       "team_domain": "<team>.cloudflareaccess.com",
       "apps_aud": "<the AUD of the Access app covering *.<your domain>>",
       "owner_email": "<your email>"
     }
   }
   ```
4. **Check:** run `woltspace doctor`. The `remote-apps` check passes once the settings are right. The `apps` check lists apps that listen on `0.0.0.0` (change them to `--host $HOST`) and apps that share a name.
5. **Check old sharing is off:** after the first boot, `woltspace doctor` shows no `app-tunnels` failure. Apps that were shared with `"public": true` are no longer shared. To share one again, run `woltspace app share <app>` and send the new link. An app's name is now a host label: lowercase letters, digits and dashes. An app whose folder or manifest name has a capital letter or `_` (0.5 took both), or starts with `site-`, can't be opened through the Mill or shared: rename it first. `woltspace doctor` names each one in its `apps` check.

Running these steps twice changes nothing the second time.
