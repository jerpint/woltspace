# Migrating to 0.6.0: the Mill

**For:** every lodge coming from 0.5.x. **Required:** yes, for anyone who reaches wolt sites or apps through a tunnel. Otherwise it's mostly links.

**Why:** a wolt's pages and apps used to run on the lodge's own origin, where their script could call the lodge's API as the owner. In 0.6 each one has an origin of its own, served by the Mill. See `docs/mill.md`.

## What changed

- **Wolt sites:**
  - Sites live at `http://<wolt>.sites.localhost:7777/`.
  - Through the tunnel, they're at `https://site-<wolt>.<your domain>/`, but only once the owner turns that on (step 4).
  - `/wolt/<wolt>/site/...` redirects there and serves nothing itself.
  - A site page is served as written: the lodge's site shell no longer wraps it.
- **Apps:**
  - Apps live at `http://<app>.localhost:7777/`, unchanged.
  - Through the tunnel, they're at `https://<app>.<your domain>/`, unchanged.
  - Both go through the Mill now.
  - `/app/<app>/` redirects there. Static apps (no `start`) are served by the Mill, without their dotfiles.
- **Sharing is explicit, and goes through the Mill:** `woltspace app share <app>` shares one app with anyone who has the link, through the lodge and the Mill (see `docs/mill.md`). `"public"` in an app's manifest no longer shares it, and `WOLTSPACE_SHARING_ENABLED` is gone. The old per-app quick tunnels, which reached an app's port directly, are retired. At first boot, the lodge stops the quick tunnels an older lodge started, but only a process whose command is still that app's quick tunnel. It clears a record only once the tunnel has stopped, and leaves that app untouched until then. `woltspace doctor` fails while one is still running.
- **Through the tunnel, the lodge checks Cloudflare Access itself:** a site or app is opened only for a valid Access token for the apps' Access application, and only for the owner's email. That needs `ways_in.cloudflare` settings (below). Without them, sites and apps through the tunnel answer `403`.
- **App names:** an app named `site-…` is no longer served, locally or through the tunnel, because the name is reserved for sites. Rename it (`woltspace doctor` names it). While it exists, the matching remote site stays off.
- **Sparks and tool pages** (`/history/…`, `/tools/…`) run in an opaque sandbox on the lodge's origin.

## Steps

1. **Rewrite your links:** a wolt rewrites its own links and notes from `/wolt/<wolt>/site/<page>` to `http://<wolt>.sites.localhost:7777/<page>`. `push-view /wolt/<wolt>/site/<page>` keeps working through the redirect. Show the owner the list of changed files before writing.
2. **Only the owner can do this, on Cloudflare:** apps and sites need an Access application covering `*.<your domain>`. If you followed `docs/wildcard-subdomain-setup.md` or the cloudflare skill, you already have one (`woltspace-apps`): reuse it. One application can also cover the lodge; a second one for the lodge is optional, and lets the two have different policies. You need the AUD tag of the one covering `*.<your domain>`: Zero Trust → Access → Applications → the application → Overview → "Application Audience (AUD) Tag" (or `result.aud` from the API). An app with an Access application of its own has a different AUD and answers `403` through the tunnel: remove that application, so the wildcard one covers the app.
3. **Only the owner can do this, in `woltspace.json`:**
   ```json
   "ways_in": {
     "cloudflare": {
       "team_domain": "<team>.cloudflareaccess.com",
       "apps_aud": "<the AUD of the Access app covering *.<your domain>>",
       "owner_email": "<your email>"
     }
   }
   ```
4. **Only the owner can do this, if you want sites through the tunnel:** first make sure no app was ever named `site-…`, since such an app's browser storage and service workers would outlive it. Then add `"mill": {"remote_sites": true}` to `woltspace.json`.
5. **Check:** run `woltspace doctor`. The `remote-apps` check passes once the settings are right. The `apps` check lists apps that listen on `0.0.0.0` (change them to `--host $HOST`) and apps that share a name.
6. **Check old sharing is off:** after the first boot, `woltspace doctor` shows no `app-tunnels` failure. Apps that were shared with `"public": true` are no longer shared. To share one again, run `woltspace app share <app>` and send the new link.

Running these steps twice changes nothing the second time.
